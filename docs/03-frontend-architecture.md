# 03 — Frontend Architecture

## Structural principle

The frontend follows the same layering discipline as the reference project, adapted from
Lambda-and-domains to React-and-hooks:

```
Pages          →  route-level containers. Own layout and view state. No data access.
Hooks          →  all server state + business rules. The only consumers of services.
Services       →  all Supabase access. The only consumers of the Supabase client.
Components     →  presentational. Receive data and callbacks as props.
```

**The rule, stated once and enforced everywhere:** a component never imports `supabase`, and never
imports a service. If a component needs *data*, it receives it from a page, which got it from a
hook. This is the same reason the reference project's Lambda handlers never touch DynamoDB
directly — a single seam makes the whole system testable and changeable.

**The rule is about data access, not about hooks in general.** Components may and must call hooks
that are purely local concerns:

| Allowed in a component | Not allowed in a component |
|---|---|
| `useState`, `useMemo`, `useRef` | `useApplications` / `useApplicationMutations` |
| `useIsMobile` (a media query, not data) | any `services/*` import |
| `@dnd-kit`'s `useDraggable` / `useDroppable` | `supabase` in any form |
| `useToast` (fire-and-forget UI feedback) | `useQuery` / `useMutation` directly |

`ApplicationCard` calling `useDraggable` is correct. `ApplicationCard` calling `useApplications` is
not — it would fetch independently of the page and defeat the single-cache-entry guarantee below.

## Constants: the single source of truth for status

Status appears in the Kanban columns, the filter chips, the badges, the form's select, and the
timeline. Defining it once prevents four copies drifting apart.

```ts
// src/constants/status.ts
import type { Database } from '../types/database.types';

export type ApplicationStatus = Database['public']['Enums']['application_status'];

// `as const` and NO type annotation — both matter. zod's z.enum() requires a
// readonly tuple of string literals; an `ApplicationStatus[]` annotation widens
// this to a mutable string[]-shaped array and z.enum(STATUS_VALUES) then fails
// to compile. See 05 § F2 Validation.
export const STATUS_VALUES = [
  'pending_application',
  'scheduled_for_interview',
  'interviewed',
  'rejected',
  'accepted',
] as const;

// Kanban column order. Identical to STATUS_VALUES today and deliberately kept as
// a separate export: column order is a presentation decision, enum membership is
// a schema fact, and they are free to diverge later.
export const STATUS_ORDER: readonly ApplicationStatus[] = STATUS_VALUES;

export const STATUS_LABELS: Record<ApplicationStatus, string> = {
  pending_application: 'Pending Application',
  scheduled_for_interview: 'Scheduled for Interview',
  interviewed: 'Interviewed',
  rejected: 'Rejected',
  accepted: 'Accepted',
};

// Tailwind classes, resolved once. See 04-design-system.md for the palette rationale.
export const STATUS_STYLES: Record<ApplicationStatus, { dot: string; badge: string }> = {
  pending_application:    { dot: 'bg-slate-400',   badge: 'bg-slate-100 text-slate-700' },
  scheduled_for_interview:{ dot: 'bg-blue-500',    badge: 'bg-blue-50 text-blue-700' },
  interviewed:            { dot: 'bg-violet-500',  badge: 'bg-violet-50 text-violet-700' },
  rejected:               { dot: 'bg-rose-500',    badge: 'bg-rose-50 text-rose-700' },
  accepted:               { dot: 'bg-emerald-600', badge: 'bg-emerald-50 text-emerald-700' },
};
```

`STATUS_ORDER` is what drives Kanban column order — changing the board layout is a one-line edit
here, not a component rewrite.

### `constants/staleness.ts`

Staleness is derived, never stored — the database records *when* the status last changed
(`status_changed_at`, [01](./01-database-schema.md)), and the client decides what counts as stale.

```ts
// src/constants/staleness.ts
import type { ApplicationStatus } from './status';

export const STALE_THRESHOLD_DAYS_DEFAULT = 14;
export const STALE_THRESHOLD_STORAGE_KEY = 'jat.staleThresholdDays';

// Terminal statuses are never stale — a Rejected application sitting untouched
// for six months is not a missed follow-up, it's just finished.
const TERMINAL: readonly ApplicationStatus[] = ['rejected', 'accepted'];

export function isStale(
  application: { status: ApplicationStatus; status_changed_at: string },
  thresholdDays: number = STALE_THRESHOLD_DAYS_DEFAULT
): boolean {
  if (TERMINAL.includes(application.status)) return false;
  const changed = new Date(application.status_changed_at).getTime();
  return Date.now() - changed > thresholdDays * 24 * 60 * 60 * 1000;
}

export function daysSinceStatusChange(statusChangedAt: string): number {
  return Math.floor((Date.now() - new Date(statusChangedAt).getTime()) / 86_400_000);
}
```

**The threshold lives in `localStorage`, not the database.** This is the app's only user preference,
and adding a `user_preferences` table plus its own RLS policies for one integer is disproportionate.
The cost is honest and small: the threshold does not sync across devices. If a second preference
ever appears, that is the moment to introduce the table — not before.

`status_changed_at` is a `timestamptz`, so `new Date(...)` parses it correctly. This is **not** the
`applied_date` timezone trap from [07](./07-component-specifications.md) — that one applies only to
date-only columns.

## Server state: TanStack Query

**Why a query library at all**, when the reference project just calls axios in a `useEffect`: this
app's central interaction is drag-and-drop, which demands optimistic updates with rollback on
failure. Hand-rolling that (plus caching, refetch-on-focus, and realtime reconciliation) is
exactly the code TanStack Query already contains. The reference project's simpler pattern is
correct for read-mostly report screens; this app is write-heavy on a single hot path.

### QueryClient configuration

```ts
// src/main.tsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: 1,                      // one retry; RLS/validation failures won't succeed on retry
      refetchOnWindowFocus: true,    // returning to the tab shows current data
    },
    mutations: {
      retry: 0,                      // never auto-retry a write
    },
  },
});
```

`refetchOnWindowFocus` is left on deliberately, and it is why [04](./04-design-system.md) specifies
that a background refetch renders **nothing** — no spinner, no dimming. Components must key their
loading UI off `isLoading` (first load, no data yet), never `isFetching` (any fetch, including
background ones), or the board will flicker every time the user tabs back.

`retry: 0` on mutations matters for the optimistic path: a retried status change would leave the
card in its optimistic position for seconds while the retry runs, then possibly roll back — the
user reads that as the app being stuck.

### Query keys

```ts
// src/hooks/queryKeys.ts
export const queryKeys = {
  applications: {
    all: ['applications'] as const,
    // `lists` is the prefix that matches EVERY list query regardless of filters/sort.
    // Optimistic updates target this, never `all` — see the warning below.
    lists: ['applications', 'list'] as const,
    list: (filters: ApplicationFilters, sort: ApplicationSort) =>
      ['applications', 'list', filters, sort] as const,
    detail: (id: string) => ['applications', 'detail', id] as const,
    history: (id: string) => ['applications', 'history', id] as const,
  },
};
```

Keys are built in one place so an invalidation can never miss a cache entry because two call sites
spelled the key differently.

> **Why `lists` exists separately from `all`.** TanStack Query matches query keys by *prefix*.
> `['applications']` matches the list queries **and** `detail(id)` (a single object) **and**
> `history(id)` (a different row type). An optimistic updater written as
> `(old) => old?.map(...)` against that prefix will hit the detail entry and throw
> `old.map is not a function` inside `onMutate` — which aborts the mutation before it ever
> fires, and TypeScript will not catch it because the `<Application[]>` type parameter on
> `setQueriesData` is an unchecked assertion. **Optimistic writes target `lists`. Invalidation
> may target `all`.**

### `useApplications` — the central read hook

```ts
// src/hooks/useApplications.ts
import { useQuery } from '@tanstack/react-query';
import { listApplications, type ApplicationFilters } from '../services/applicationsService';
import { queryKeys } from './queryKeys';
import { STATUS_ORDER, type ApplicationStatus } from '../constants/status';
import type { Application } from '../services/applicationsService';

export function useApplications(
  filters: ApplicationFilters = {},
  sort: ApplicationSort = DEFAULT_SORT
) {
  const query = useQuery({
    queryKey: queryKeys.applications.list(filters, sort),
    queryFn: () => listApplications(filters, sort),
    staleTime: 30_000,
    placeholderData: keepPreviousData, // v5: keeps the old list on screen while re-sorting
  });

  // Grouping for the Kanban board is derived here, not in the component, so
  // both views consume the same fetch and can never disagree about the data.
  const byStatus = useMemo(() => {
    const groups = Object.fromEntries(
      STATUS_ORDER.map((s) => [s, [] as Application[]])
    ) as Record<ApplicationStatus, Application[]>;

    for (const app of query.data ?? []) groups[app.status].push(app);
    return groups;
  }, [query.data]);

  return {
    applications: query.data ?? [],
    byStatus,
    isLoading: query.isLoading,
    isError: query.isError,
    error: query.error as Error | null,
    refetch: query.refetch,
  };
}
```

### Sorting, and what "one fetch, two views" actually guarantees

Sort is part of the query key, because sorting happens in the database. That has a consequence
worth stating plainly rather than discovering later:

**The Kanban board always uses `DEFAULT_SORT` (`created_at desc`) and never varies it.** Only the
Table view exposes sort controls. This is a deliberate decision, and it resolves what would
otherwise be a contradiction:

- Kanban card order within a column is fixed (`created_at desc`) — [05](./05-features-and-workflows.md), F4.
- If the table's sort were shared with the board, changing the table's sort to "Company" would
  silently reorder every Kanban column too.
- And because sort is in the query key, a shared sort would mean toggling views after sorting
  refetches.

**So the guarantee is precise:** with the table at its default sort, both views hit the same cache
entry and toggling refetches nothing. If the user has changed the table's sort, switching to the
board uses the board's own (default-sorted) entry — which is usually already cached from earlier in
the session, and if not, `keepPreviousData` means the previous data stays on screen while it loads
rather than flashing a skeleton.

This is the honest version. The alternative — sorting client-side to preserve a single cache entry
— was rejected because it breaks down badly past a few hundred rows and would have to be undone
later.

### `useApplicationMutations` — writes, with optimistic status changes

```ts
// src/hooks/useApplicationMutations.ts
export function useApplicationMutations() {
  const queryClient = useQueryClient();

  const invalidate = () =>
    queryClient.invalidateQueries({ queryKey: queryKeys.applications.all });

  const create = useMutation({
    mutationFn: createApplication,
    onSuccess: invalidate,
  });

  const update = useMutation({
    mutationFn: ({ id, patch }: { id: string; patch: ApplicationUpdate }) =>
      updateApplication(id, patch),
    onSuccess: invalidate,
  });

  const remove = useMutation({
    mutationFn: deleteApplication,
    onSuccess: invalidate,
  });

  // Archive/unarchive. Optimistic like changeStatus, because the row must leave
  // (or enter) the current view immediately — a round-trip delay here reads as
  // "the button didn't work" and invites a second click.
  const setArchivedMutation = useMutation({
    mutationFn: ({ ids, isArchived }: { ids: string[]; isArchived: boolean }) =>
      setArchived(ids, isArchived),

    onMutate: async ({ ids, isArchived }) => {
      await queryClient.cancelQueries({ queryKey: queryKeys.applications.lists });
      const previous = queryClient.getQueriesData<Application[]>({
        queryKey: queryKeys.applications.lists,
      });

      queryClient.setQueriesData<Application[]>(
        { queryKey: queryKeys.applications.lists },
        (old) =>
          Array.isArray(old)
            ? old.map((a) => (ids.includes(a.id) ? { ...a, is_archived: isArchived } : a))
            : old
      );

      return { previous };
    },

    onError: (_e, _v, context) =>
      context?.previous.forEach(([key, data]) => queryClient.setQueryData(key, data)),

    onSettled: invalidate,
  });

  // One request, one rollback — see the bulk-actions note in doc 05 F5.
  const bulkStatus = useMutation({
    mutationFn: ({ ids, status }: { ids: string[]; status: ApplicationStatus }) =>
      bulkUpdateStatus(ids, status),

    onMutate: async ({ ids, status }) => {
      await queryClient.cancelQueries({ queryKey: queryKeys.applications.lists });
      const previous = queryClient.getQueriesData<Application[]>({
        queryKey: queryKeys.applications.lists,
      });

      queryClient.setQueriesData<Application[]>(
        { queryKey: queryKeys.applications.lists },
        (old) =>
          Array.isArray(old) ? old.map((a) => (ids.includes(a.id) ? { ...a, status } : a)) : old
      );

      return { previous };
    },

    onError: (_e, _v, context) =>
      context?.previous.forEach(([key, data]) => queryClient.setQueryData(key, data)),

    onSettled: invalidate,
  });

  const importMany = useMutation({
    mutationFn: bulkCreate,
    onSuccess: invalidate,
  });

  // The hot path: dragging a card must feel instant.
  const changeStatus = useMutation({
    mutationFn: ({ id, status }: { id: string; status: ApplicationStatus }) =>
      updateApplicationStatus(id, status),

    onMutate: async ({ id, status }) => {
      // NOTE: `lists`, not `all`. See the query-key warning above — targeting
      // `all` reaches the detail/history entries and throws inside onMutate.
      await queryClient.cancelQueries({ queryKey: queryKeys.applications.lists });
      const previous = queryClient.getQueriesData<Application[]>({
        queryKey: queryKeys.applications.lists,
      });

      queryClient.setQueriesData<Application[]>(
        { queryKey: queryKeys.applications.lists },
        (old) => (Array.isArray(old) ? old.map((a) => (a.id === id ? { ...a, status } : a)) : old)
      );

      return { previous };
    },

    onError: (_err, _vars, context) => {
      // Put every touched cache entry back exactly as it was.
      context?.previous.forEach(([key, data]) => queryClient.setQueryData(key, data));
    },

    onSettled: invalidate,
  });

  return {
    create,
    update,
    remove,
    changeStatus,
    setArchived: setArchivedMutation,
    bulkStatus,
    importMany,
  };
}
```

**The three-callback contract matters and should not be simplified:** `onMutate` snapshots and
applies the optimistic change, `onError` restores the snapshot so a failed drag visibly snaps the
card back, and `onSettled` reconciles with the server regardless of outcome — which is also what
picks up the `updated_at` value and the new `status_history` row that the database triggers wrote.

### Realtime, reconciled correctly

```ts
// src/hooks/useRealtimeApplications.ts
export function useRealtimeApplications() {
  const { user } = useAuth();
  const queryClient = useQueryClient();

  useEffect(() => {
    if (!user) return;
    return subscribeToApplications(user.id, () => {
      // Invalidate, never hand-patch. A realtime event and an in-flight optimistic
      // update writing to the same cache from two directions is how ghost cards
      // and duplicated rows happen.
      queryClient.invalidateQueries({ queryKey: queryKeys.applications.all });
    });
  }, [user, queryClient]);
}
```

Mounted once, in `ApplicationsPage`. Not in individual cards.

## Filter and sort state, synced to the URL

```ts
// src/hooks/useApplicationFilters.ts
export function useApplicationFilters() {
  const [searchParams, setSearchParams] = useSearchParams();

  const filters: ApplicationFilters = {
    status: searchParams.getAll('status') as ApplicationStatus[],
    platform: searchParams.getAll('platform') as PlatformSource[],
    search: searchParams.get('q') ?? undefined,
  };

  const sort = {
    field: (searchParams.get('sort') ?? 'created_at') as SortField,
    direction: (searchParams.get('dir') ?? 'desc') as 'asc' | 'desc',
  };

  const view = (searchParams.get('view') ?? 'kanban') as 'kanban' | 'table';

  // setters omitted for brevity — each writes back into searchParams
  return { filters, sort, view, setFilters, setSort, setView };
}
```

Putting this state in the URL rather than `useState` means a filtered view is shareable and
bookmarkable, survives a refresh, and makes the browser back button behave the way users expect
after opening a detail drawer. It costs nothing extra to implement and removes a whole category of
"why did my filters reset" complaints.

## Auth context and route protection

```tsx
// src/context/AuthContext.tsx  (shape)
type AuthContextValue = {
  user: User | null;
  session: Session | null;
  isLoading: boolean;
  signIn: (email: string, password: string) => Promise<void>;
  signUp: (email: string, password: string) => Promise<void>;
  signOut: () => Promise<void>;
};
```

The provider subscribes to `supabase.auth.onAuthStateChange` and holds the session — mirroring the
reference project's `AuthContext.jsx`, which likewise centralizes session restore and a
session-expired path rather than scattering token checks through pages.

```tsx
// src/components/layout/ProtectedRoute.tsx
export function ProtectedRoute({ children }: { children: ReactNode }) {
  const { session, isLoading } = useAuth();
  if (isLoading) return <FullPageSpinner />;
  if (!session) return <Navigate to="/login" replace />;
  return <>{children}</>;
}
```

**`isLoading` must be handled explicitly.** Rendering `<Navigate>` while the session is still being
restored from storage bounces an already-signed-in user to the login screen on every refresh — a
classic and very visible bug.

## Responsive strategy

Breakpoints follow Tailwind defaults; the view logic hinges on one:

| Width | Kanban view | Table view |
|---|---|---|
| `< 768px` (mobile) | `MobileStatusTabs` — one status column at a time, tab bar to switch | Card list, not a table — each row becomes a stacked card |
| `768px – 1023px` (tablet) | Horizontally scrollable columns, ~2.5 visible | Real table, fewer columns (company, title, status, date) |
| `≥ 1024px` (desktop) | All five columns, horizontally scrollable below 1712px | Full table, all columns |

**On "all five columns visible":** five 320px (`w-80`) columns plus four 16px gaps plus 48px of page
padding needs **1712px** of viewport — wider than most laptop screens. Rather than pretend
otherwise, the board is a horizontally scrolling region at every desktop width, and simply stops
scrolling once the viewport exceeds 1712px.

The alternative — fluid columns that shrink to fit — was rejected: below roughly 280px a card's
company name and job title start wrapping to three lines each, and the board becomes harder to scan
than a scrolling one. A fixed column width with a scroll is the honest trade.

```ts
// src/hooks/useMediaQuery.ts
export const useIsMobile = () => useMediaQuery('(max-width: 767px)');
```

**Drag-and-drop on mobile is deliberately not the primary interaction.** Dragging a card between
tabbed columns on a small touch screen is fiddly and error-prone. On mobile, status changes happen
through the card's status control (a tap-to-open menu) — `@dnd-kit` still works with touch
sensors, but the design does not depend on it. See [04](./04-design-system.md).

## Testing conventions

Match the reference project: behavior-focused, colocated, RTL queries by role and text rather than
test ids.

```
ComponentName.tsx
ComponentName.test.tsx
```

**What gets tested:**

| Layer | Approach |
|---|---|
| Services | Mock `supabaseClient`; assert query shape and that errors normalize into `AppError`. |
| Hooks | `renderHook` with a `QueryClientProvider` wrapper and mocked services; assert optimistic update applies then rolls back on rejection. |
| Components | Render with props; assert what a user sees and can do. No mounting of real providers unless the test is about them. |
| Forms | Assert validation messages appear for invalid input and that submit is blocked, mirroring the reference project's approach of testing that validation surfaces rather than that submit is disabled. |

**The one test this project must not ship without:** a test asserting that
`changeStatus` rolls the card back to its original column when the mutation rejects. That path is
invisible in manual happy-path testing and is exactly where a drag-and-drop board loses user trust.

## Performance notes

At the expected scale (hundreds of applications per user, not thousands), avoid premature
optimization. Two things are worth doing from the start:

- **`React.memo` on `ApplicationCard`.** During a drag, `@dnd-kit` re-renders frequently; memoizing
  the card on `application.id` and `application.updated_at` keeps that cheap.
- **Filter and sort in the database, not the client**, via the service layer's query builder —
  already the design in [02](./02-backend-architecture.md). Client-side filtering of a full table
  scan works fine at 50 rows and degrades badly at 500, and switching later means rewriting the
  hook.

What *not* to do in v1: virtualized lists, code splitting beyond route level, or memoizing every
component. None are justified at this data scale.
